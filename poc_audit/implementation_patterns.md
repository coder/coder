# Implementation Patterns

Recorded 2026-08-20. This document states how the tables and the code over them
are built: the shape a journal takes, what the schema is made to enforce rather
than merely document, and where the existing implementation and this corpus are
misaligned.

It exists because schema is the part of this work most prone to being argued
again from the beginning. A pattern settled once and written here is one that
does not have to be settled a second time, and a reader who disagrees with a
pattern has somewhere to say so.

Sections are separated by the standing of their contents. **Established**
records positions that have been decided. **Derived** records reasoning built
on top of them, which is offered for challenge rather than settled.
**Findings** records verifiable facts about the existing codebase. **Open**
records questions not yet answered.

What a particular entity's tables hold belongs in `entity_model.md`. This
document is about the shape, not the contents.

## Established

### A table is named for its entity, its aspect, and its kind of book

`authorization_lifecycle_journal` and `authorization_lifecycle_ledger`: the
entity, then what about it is being recorded, then whether the table is a book
of original entry or the derived view of current state.

The aspect is not decoration. Nothing says a lifecycle is the only thing worth
recording about an authorization, and a name that leaves it out would have to
change the first time something else is.

### A ledger keeps its retired rows, in one table

A ledger holds every entity of its kind whatever state it is in, not only those
currently alive.

The reason is about posting rather than about storage. Every entry posts to the
ledger, and were the ledger to hold only living entities then the entry ending
a life would have to delete a row rather than update one. Posting would then
carry an exception, and an exception in posting is worse than any quantity of
retained rows.

**One table, not a current one and a retired one.** Splitting a lifecycle
ledger reintroduces at the physical level the exact exception the rule above
removes, since termination becomes a move rather than an update. The state
column already distinguishes the two sets, a second table would have to receive
every future column twice, and any question about an entity's history would
need a union.

Where volume eventually makes it worth keeping the living set small, Postgres
declarative partitioning by list on the state column gives that without a
second logical table, and moves a row between partitions on update. Converting
an existing table to a partitioned one calls for a rewrite, which costs less
here than elsewhere: a ledger is derived from its journal and can be rebuilt
from it.

### These patterns bind every journal

Each pattern below applies to **every journal**, whether or not the journal
being written appears to need it. There is one journal per entity, so the
alternative is a set of journals that differ from each other for no reason but
the order they were written in.

Adopting a pattern late is not merely a migration. It is a migration plus a
body of entries already written under the old shape, which cannot be rewritten
because a journal is append only.

### The entry identifier comes from an explicit sequence

An entry identifier is drawn from a named sequence with a single `nextval`
call, and the value is then used for every line of that entry.

`BIGSERIAL` cannot serve, because it allocates per row and the lines of one
entry must share a value. `GENERATED BY DEFAULT AS IDENTITY` could be pressed
into service, but it forces the first line to be inserted alone so its value
can be read back before the rest are written, which orders the inserts around a
bookkeeping detail. A named sequence states in the schema what the number is,
an identifier for an entry rather than for a row.

### Lines are numbered from zero

The line number is a `smallint` checked non negative, and the first line of
every entry is line `0`. The primary key is the entry identifier together with
the line number. A line has no identity of its own, because a line is not a
thing: it is part of one.

### Journals are denormalized across their lines

An entry may have more than one line. **Lines are rows of the journal table
sharing an entry identifier**, not rows of a separate table under a foreign
key.

A multiline entry expresses an **atomic group**. The lines are one event and
not several that happen to coincide. This matters most where an entry both ends
something and begins something: the authorized activity has no gap, because the
group describes a single interval rather than two intervals sharing an
endpoint.

### Entry level values are written once, on line zero

Denormalization puts every column on every row, so placement by level cannot be
expressed in the schema. It is therefore a rule about what is written:
**material belonging to the entry appears only on line `0`**, every later line
holds null in those columns, and a reader wanting such a value for a later line
takes it from line `0`. The single exception is the entry identifier, which
every line carries, because carrying it is what makes them one entry.

Entry level means the recording date, the effective date, and the actor. Line
level means the event and the subject. One entry has one actor: no case has
been found where two actors act at the same instant, and if one is found this
is where it will have to be revisited.

The rule buys one thing: a value written once cannot disagree with itself. A
value repeated across lines can, and then a reader has to decide which copy to
believe.

**The write half of the rule is a constraint.** Each entry level column carries
a row level check tying it to the line number, of the form `CHECK ((line = 0) =
(recording_date IS NOT NULL))`. One named check per column rather than one
covering all of them, so that a violation names the column that caused it.

That interacts with `DEFAULT now()`, and the resolution is two insert
statements. Line `0` is inserted by a statement omitting the recording date, so
the default fires and no caller can reach it. Later lines are inserted by a
statement writing a literal null, not a parameter, so no caller can reach it
there either. Both guarantees survive at the cost of a second statement for a
multiline entry.

**The read half is not expressible** and stays documentation: nothing can make
a query take a later line's values from line `0`.

**Post proof of concept this wants helper functions in Go**, so that no call
site is left to remember which statement to use. The constraints catch a
violation where it is made, but they do not make the rule easy to follow.

### A reference standing where a foreign key would stand is a pair

Wherever a column refers to an entity that could be of more than one kind, it
holds a `(type, identifier)` pair. `entity_model.md`, under "An entity identity
is always a pair", gives the rule and the reason SQL forces it: there is no way
to declare a key into a union of identity tables.

The discipline that follows is the pattern: **never assume that one kind of
entity will forever be the only kind in a given position.** An authorization's
principal is a user today and its agent is an AI agent today, and neither fact
is a reason to write a column that can hold nothing else. This covers every
actor position, actors being the commonest case.

A journal's subject is not an exception to this. It is self reference: one
journal per entity means the journal is about a single kind, and the table's
name already says which. Nothing is standing in for a key into a union, so the
rule does not reach it and there is no exception to remember.

### A ledger row names the entry that last posted to it

Bookkeeping cross references its two books in both directions. The journal's
folio column names the ledger account posted to, and the ledger's names the
journal page the posting came from. The reference is written as each amount is
posted, which makes the column double as a control: it shows which lines have
been transferred and which have not.

Both directions exist here. A journal entry's subject is the identifier of the
ledger row, and the ledger's `posting_reference` holds the identifier of the
entry most recently posted to it.

It buys two things. Reconciliation gets a cheap handle, since an entry newer
than the reference on the row it concerns is an entry not yet posted. And
posting can be made safe against a race: an update conditioned on the reference
it expects to find will fail for the second of two concurrent posters rather
than letting both appear to succeed. Such a race would almost certainly be a
defect rather than a legitimate pattern, which is not a reason to let it corrupt
a row in silence.

**No foreign key, and none is available.** A journal's primary key is the entry
identifier together with the line number, so the entry identifier alone is not
unique, and it cannot be made unique because the lines of one entry share it.

### The recording date is set by the schema, not by a caller

`recording_date` is declared with `DEFAULT now()` and is **never a parameter**,
so no caller can supply it, override it, or backdate it. The line `0` statement
omits the column and takes the default; the statement for later lines writes a
literal null, as described above.

`audit_approach.md`, under "Two dates on every entry", states this as a rule.
Making the schema enforce it costs nothing and removes the only way it could be
broken.

`effective_date` is the opposite case. It is always required, it is ordinarily
an explicit parameter because only the caller knows it, and it defaults to
`now()` where the caller has nothing better to offer.

Postgres `now()` is transaction start time and is constant across a
transaction, so entries written to different journals in one transaction carry
an identical recording date. That is a property to know about rather than one
to rely on; see Open below.

## Findings

### The existing journal carries one date, not two

`coderd/database/migrations/000571_entity_journal.up.sql` declares `recorded_at
timestamptz NOT NULL` and nothing else temporal. The corpus now requires two
dates under different names. The journal also has no line number and no entry
identifier distinct from its row identifier: `id BIGSERIAL PRIMARY KEY` is
both.

### Two ad hoc history tables already do this work for one entity

`user_status_changes` and `user_deleted` are in the category of this approach,
built for one entity rather than on principle. **They should eventually be
incorporated into it.** What they do today may not match the eventual design in
detail, but the new system should be able to do everything they currently do,
consistently rather than case by case.

### Both identifier mechanisms have precedent here

`000519_chatd_core_state_machine.up.sql` creates a named sequence and attaches
it with `ALTER COLUMN ... SET DEFAULT nextval(...)`.
`000569_ai_sandbox_audit.up.sql` uses `BIGINT GENERATED ALWAYS AS IDENTITY`.
Eight migrations use `BIGSERIAL`. Choosing the sequence is therefore consistent
with the codebase rather than novel in it.

## Open

### Whether journal subjects carry a foreign key

**Left out for now, deliberately**, pending more code to judge by. Per-entity
journals make a real key possible, since such a journal has only one kind of
subject, and a key would let the database enforce what a `(type, identifier)`
pair can only describe.

The complication to carry into that decision is ordering. A key requires the
ledger row to exist before the entry that records its creation, and the entry
is the book of original entry. `DEFERRABLE INITIALLY DEFERRED` checks at commit
rather than at statement time, so the entry can still be written first; the
option is available whenever the decision is taken.

### Whether transaction time is relied on for grouping

Entries written to different journals in one transaction share a recording
date, which recovers the grouping that was deliberately not given a shared
identifier. Whether anything should depend on that is unsettled, and the limit
is that a shared timestamp is evidence of a shared transaction rather than
proof, since two unrelated transactions can begin within one clock tick. The
question belongs to forensic analysis, which this work has not reached.
